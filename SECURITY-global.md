# Hiero Security Policy

This document defines how security vulnerabilities are reported and handled in
[Hiero](https://hiero.org), a project of [LF Decentralized Trust](https://www.lfdecentralizedtrust.org).
It aligns with the [LF Decentralized Trust Security Policy](https://lf-decentralized-trust.github.io/governance/governing-documents/SECURITY-POLICY)
and follows the recommendations of the [OpenSSF Vulnerability Disclosure Working Group](https://github.com/ossf).

**Looking for where to report a vulnerability?** Check the `SECURITY.md` file of the repository
in question. It always takes precedence over this document. See [Which rules apply to which repository](#which-rules-apply-to-which-repository).

## Which rules apply to which repository

The repositories in the `hiero-ledger` organization fall into two categories: repositories
covered by the Hedera Bug Bounty Program, and repositories with project-specific security
handling. The category of every repository is listed in the
[repository registry](<link to registry>).

### Category A – Hedera Bug Bounty Program

Some repositories are covered by the **[Hedera Bug Bounty Program](https://immunefi.com/bug-bounty/hedera/)**
on Immunefi. Their maintainers have decided to handle all security reports exclusively through
that program. GitHub private vulnerability reporting is disabled for these repositories.

The authoritative list of covered repositories is the
[scope page of the program](https://immunefi.com/bug-bounty/hedera/scope/#assets). At the time
of writing, these are:

- [hiero-consensus-node](https://github.com/hiero-ledger/hiero-consensus-node)
- [hiero-mirror-node](https://github.com/hiero-ledger/hiero-mirror-node)
- [hiero-json-rpc-relay](https://github.com/hiero-ledger/hiero-json-rpc-relay)
- [hiero-cryptography](https://github.com/hiero-ledger/hiero-cryptography)
- [hiero-sdk-java](https://github.com/hiero-ledger/hiero-sdk-java)
- [hiero-sdk-js](https://github.com/hiero-ledger/hiero-sdk-js)
- [hiero-sdk-go](https://github.com/hiero-ledger/hiero-sdk-go)

Immunefi may charge a submission fee for researchers without an established reputation. If you
cannot pay the fee, see the `SECURITY.md` of the repository for how to request a waiver.

### Category B – Project-specific security handling

All other repositories. The maintainers of each repository decide how they handle security
reports and which level of security support they offer, from "best effort, upstream fixes only,
no guaranteed response" to coordinated disclosure with supported releases. The `SECURITY.md` of
each repository describes the reporting channel, the support level and how fixes are delivered.
No bounty is paid.

Repositories maintained by Hashgraph use a common Hashgraph template for their `SECURITY.md`.
Community-maintained repositories use the community template with predefined support levels.

### Repositories without their own `SECURITY.md`

There is no third category. A repository without its own `SECURITY.md` belongs to category B
and is handled at the lowest support level:

- Security fixes are only provided upstream (main branch / next release).
- A response to security reports is not guaranteed.
- The repository is not part of any bug bounty program.

The maintainers of such a repository are expected to add their own `SECURITY.md` based on the
[community template](<link to template>).

## Rules for all repositories

> [!WARNING]
> **Do not disclose vulnerabilities in public**
>
> Never report security vulnerabilities in public GitHub issues, pull requests, pull request
> comments, discussions, Discord or any other public channel.
>
> Public content that contains vulnerability or exploit details will be removed. The reporter
> will be contacted and pointed to the correct channel, and LF Decentralized Trust will be
> informed. Repeated public disclosure after a warning can lead to the account being blocked from
> the Hiero GitHub organization.

> [!WARNING]
> **AI-generated reports**
>
> You are welcome to use AI tools in your research. You are not welcome to forward their output
> without validating it.
>
> Reports that are generated by AI tools and not verified by the reporter **will be closed
> without further review and without a response**. This includes reports that
>
> - do not contain a proof of concept or exact steps to reproduce,
> - describe theoretical issues without showing that they can be reached in the code,
> - do not reference the affected version or code, or
> - show signs of being generic AI output that the reporter has not understood.
>
> Repeated submission of such reports can lead to the account being blocked.

> [!WARNING]
> **Every repository documents its security handling**
>
> Every repository must have a `SECURITY.md` that states its category, its reporting channel and
> what reporters can expect. A repository that does not guarantee any response is fine, as long
> as this is documented.

## Security team

The Hiero security team is the security team of the whole Hiero project and covers all
repositories in the `hiero-ledger` organization, regardless of their category. It

- owns this security policy and the repository templates,
- handles the reports for category A repositories together with the Hedera Bug Bounty Program,
- supports and advises the maintainers of category B repositories,
- acts on public disclosures and AI-generated report campaigns in any repository,
- maintains the embargo list and coordinates CVEs and public disclosure, and
- is the point of contact for LF Decentralized Trust on all security topics.

For category B repositories, the maintainers of each repository remain responsible for handling
the reports in their repository as described in its `SECURITY.md`.

The security team consists of the members of the following GitHub teams:

| Team | Role |
|------|------|
| [@hiero-ledger/security-maintainers](https://github.com/orgs/hiero-ledger/teams/security-maintainers) | Project maintainers responsible for receiving, triaging and remediating security reports |
| [@hiero-ledger/lf-staff](https://github.com/orgs/hiero-ledger/teams/lf-staff) | LF Decentralized Trust staff acting as security advisors and community architects |

The membership of these two teams defines the security team. There is no separate list of
members. The `security-maintainers` team must include at least three project maintainers.
Changes to the team membership follow the regular
[Hiero governance process](https://github.com/hiero-ledger/governance). See the
[People Infrastructure](https://lf-decentralized-trust.github.io/governance/governing-documents/SECURITY-POLICY#people-infrastructure)
section of the LF Decentralized Trust Security Policy for background.

### Responsibilities

For reports received through a private channel of a Hiero repository, the security team (for
category A) or the maintainers of the repository together with the security team (for category B
repositories that offer coordinated disclosure):

1. Acknowledges the receipt of the report within the time stated in the repository's
   `SECURITY.md`.
2. Assesses the report and engages with the reporter to clarify open questions. If the report
   is not a vulnerability, the reporter is informed.
3. Agrees on an embargo period with the reporter for complex issues.
4. Sets up private patch development if necessary (see [Private patch development](#private-patch-development)).
5. Requests a CVE (see [CVEs and public disclosure](#cves-and-public-disclosure)).
6. Decides on the date of public disclosure.
7. Notifies the members of the [embargo list](#embargo-list) before the disclosure.
8. Publishes a release that fixes the vulnerability.
9. Discloses the vulnerability publicly within 48 hours after the release.

For category A repositories, these steps are coordinated with the Hedera Bug Bounty Program.

`SECURITY.md` of the affected repository.

## Embargo list

Hiero maintains a private embargo list. Its members are informed about vulnerabilities and
upcoming fixes before public disclosure. This is especially relevant for operators of networks
built on Hiero.

To be added to the embargo list, send an email to the address in [Contact](#contact), including
the project name (Hiero) and the reason for your request. Requests are assessed by the security
team together with LF Decentralized Trust staff. See the Embargo List section of the
[LF Decentralized Trust Security Policy](https://lf-decentralized-trust.github.io/governance/governing-documents/SECURITY-POLICY)
for details.

## CVEs and public disclosure

Hiero uses GitHub as its CVE Numbering Authority (CNA) and publishes fixed vulnerabilities as
[GitHub Security Advisories](https://docs.github.com/en/code-security/security-advisories)
in the affected repository.

## Private patch development

Fixes for vulnerabilities are developed privately using the
[private development features of GitHub](https://docs.github.com/en/code-security). If
additional private infrastructure is needed, the responsible team contacts the
[LF Decentralized Trust Community Architects](mailto:community-architects@lfdecentralizedtrust.org).
